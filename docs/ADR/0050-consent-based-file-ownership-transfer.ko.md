# ADR 0050: 동의 기반 파일 소유권 이전

- Status: Accepted — implemented (백엔드만; 프론트엔드/admin UI는 별도 추적)
- Date: 2026-09-04
- Amends: [ADR 0024](0024-account-cascade-fk-refusal.ko.md) (그 Consequences가 열어둔 질문을
  해소함 — `23503` → 409 `USER_FILES_IN_USE` 번역은 그대로 필요하고 변경 없음. 왜 supersede가
  아니라 amend인지는 아래 Consequences 참고)
- English: [0050-consent-based-file-ownership-transfer.md](0050-consent-based-file-ownership-transfer.md)

## Context

`UpdateFileDto.userId`는 이 프로젝트의 첫 커밋(`434c2bcec0a4c6571615128fc2eda687037ff8b3`)
때부터 있었다 — 어떤 이유로 나중에 추가된 기능이 아니라 원래 CRUD 스캐폴딩이었다.
[ADR 0007](0007-ownership-checks-without-rbac.ko.md)이 이걸 언급하는 유일한 ADR인데,
그마저도 가드가 creator-only라는 것만 말한다. [ADR 0024](0024-account-cascade-fk-refusal.ko.md)는
이 필드를 실제 결과와 연결지었다 — 파일을 참조하는 게시글의 creator와 파일 자체의 creator가
달라지면 `ADR 0023` D1이 기대던 게시글↔파일 동일 작성자 invariant가 깨진다 — 그리고 "이 필드가
애초에 존재해야 하는가"를 명시적으로 열어둔 채, 필드를 제거하면 자신의 `23503` 번역 분기가
도달 불가능한 가드가 된다고 표시해뒀다.

이 ADR을 위한 조사(2026-09-04)에서 이전에 기록된 적 없던 두 가지를 확인했다:

- **실제로 이 필드를 보내는 클라이언트가 하나도 없다.** `frontend/`와 `admin/` 전체를 grep한
  결과 `PATCH /file/:id` body에 `userId`를 담는 호출 지점이 전혀 없다 —
  `frontend/src/api/types.ts` 자체 주석이 이 앱의 UI가 "아직 \[그걸\] 쓰지 않는다"고 확인해준다.
  지금 이 이전을 발동시키는 유일한 방법은 Swagger "Try it out"이나 curl 같은 직접 API 호출뿐이다.
- **동의 절차가 없다.** creator(또는 admin)가 수신자의 관여 전혀 없이 어떤 계정에게도 파일을
  강제로 떠안길 수 있다 — `file.service.ts`의 `updateFile`은 대상 유저가 존재하는지만
  확인할 뿐 그 외엔 아무것도 확인하지 않는다.

개발자가 이 필드의 실질적 의도를 처음으로 밝혔다: 계정을 삭제하거나 탈퇴하려는 사용자가,
소유한 파일을 계정 삭제 캐스케이드([ADR 0020](0020-account-deletion-cascade.ko.md))로
잃는 대신, 다른 계정에게 넘길 수 있게 하려는 것 — 파일을 지키려고 계정을 억지로 살려둘
필요가 없도록.

## Decision

### D1 — 즉시 강제 이전을 제안 → 수락/거절/취소 흐름으로 교체

`UpdateFileDto.userId`(즉시, 무동의 강제 이전)를 제거한다. 대신: creator(또는 admin)가 특정
대상에게 이전을 *제안*하고, 오직 그 대상만 *수락*(소유권 이동)하거나 *거절*(소유권 불변)할
수 있으며, 제안자는 대상이 응답하기 전까지 언제든 *취소*할 수 있다. admin을 포함해 어떤
주체도 대상의 수락 없이 강제로 이전을 완료시킬 수 없다.

### D2 — 스키마: nullable 컬럼 하나, 파일당 대기 대상 한 명

`FileEntity`에 `pendingTransferToUserId`(nullable, UserEntity FK)를 추가한다. 별도 요청
테이블이 아니라 nullable 컬럼 하나인 이유: 이 프로젝트는 한 파일을 여러 후보에게 동시에
제안해야 할 필요를 말한 적이 없고, 평범한 컬럼이면 "대기중인가"가 join 없는 저렴한
null-check로 끝난다. 직접적인 결과는 정책적 선택이 아니라 구조적 사실이다 —
**파일 하나는 동시에 대기중인 대상을 최대 한 명만 가질 수 있다.**

### D3 — 중복 제안은 거부, 자동 덮어쓰기 아님

이미 대기중인 상태에서 새로 제안하면 409로 거부되며, 기존 대기 대상을 응답에 명시한다 —
새 후보로 조용히 재타겟팅하지 않는다. 제안자는 새 제안을 만들기 전에 기존 제안을 명시적으로
취소해야 한다. 대상이 바뀌는 게 늘 눈에 보이는 의도적 단계(제안자가 직접 호출한 `cancel`)가
되도록 자동 덮어쓰기 대신 이 방식을 택했다 — 다른 사람에게 제안한 부수 효과로 대상이
바뀌는 일은 없다.

### D4 — 관리자도 같은 동의 게이트를 거침, 강제 이전 우회 경로 없음

관리자는 이전을 *제안*할 수 있다(이 프로젝트 전반의 creator-or-admin 쓰기 패턴과 동일 —
[ADR 0007](0007-ownership-checks-without-rbac.ko.md)), 다만 수락은 언제나 대상 유저 본인의
결정이다. 대상의 동의 없이 이전을 완료시키는 별도 관리자 경로는 없다. 이건 필드의 기존
동작(관리자가 강제로 재배정 가능했던 것)에서 의도적으로 좁힌 것이다 — 이게 없애는 게
무엇인지는 아래 Consequences에 기록했다.

### D5 — `DELETE /user/:id?deleteFiles=true`가 대기중인 이전을 무시하고 우선

`deleteFiles=true`로 계정을 삭제할 때, 그 계정의 파일 중 하나가 아직 응답 없는 대기중인
이전을 갖고 있어도, 삭제는 지금과 똑같이 진행된다 — 그 파일(과 대기 상태)은 캐스케이드가
이미 지우는 나머지 전부와 함께 삭제된다([ADR 0020](0020-account-deletion-cascade.ko.md)).
캐스케이드에는 새 분기도, 새 대기 상태도, 부분 완료 모드도 생기지 않는다. 대기중인 이전이
살아남길 원하는 사용자는 계정을 삭제하기 전에 그걸 수락받거나(또는 `deleteFiles`를 아예
안 줘서 지금처럼 `USER_HAS_FILES` 409를 받거나) 해야 한다 — 이건 D1이 애초에 가능하게 하려는
"먼저 이전 마무리하기"라는 규율 그대로이지, 이 결정이 새로 만든 게 아니다.

### D6 — 새 알림 인프라 없음, 감사 로그는 수락 시점만 기록

대상은 대기중인 제안을, 제안자는 결과를 이 앱이 이미 상태를 보여주는 것과 같은 방식으로
안다 — 자기 파일 목록을 보는 것. 이메일이나 푸시 알림 시스템은 도입하지 않는다 — 이
프로젝트는 외부 API 연동이 전혀 없고(CLAUDE.md > Engineering Principles > Reliability >
Retry Limits/Timeout), 그런 걸 새로 만드는 건 이 결정의 범위를 훨씬 넘어선다.

새 감사 로그 액션 `FILE_TRANSFER`를 `AUDIT_ACTIONS`에 추가한다(`targetType: 'file'`,
[ADR 0045](0045-audit-log-target-type.ko.md)의 discriminator), 그리고 **소유권이 실제로
바뀌는 순간(수락)에만** 기록한다 — 이 로그가 제안이나 의도가 아니라 상태 변화를 기록한다는
기존 관례와 일치한다([ADR 0013](0013-rbac-and-audit-log.ko.md)/[0045](0045-audit-log-target-type.ko.md)).
이전 소유자의 계정이 나중에 삭제되고 나면, 그 파일이 원래 누구 것이었는지 알 수 있는 유일한
곳이 바로 이 로그다 — 그 이후엔 `FileEntity.creator`가 현재 소유자만 보여줄 뿐, 자체 이력
컬럼이 없다.

## Consequences

- **[ADR 0024](0024-account-cascade-fk-refusal.ko.md)의 `23503` → 409 `USER_FILES_IN_USE`
  번역은 그대로 필요하고 변경되지 않는다.** 이전을 동의 뒤로 게이트한다고 해서 게시글↔파일
  동일 작성자 invariant가 복원되진 않는다 — B가 수락하는 순간 `FileEntity.creator`는 예전
  무동의 필드가 옮기던 것과 정확히 같은 방식으로 B로 넘어가고, 그 파일을 여전히 참조하는
  A의 게시글은 ADR 0024가 서술한 것과 똑같이 새 소유자와 어긋난다. 이 결정이 바꾸는 건
  *누가 이전을 트리거할 수 있는지*와 *먼저 무엇을 얻어야 하는지*(대상의 동의)일 뿐 — 이전이
  실제로 일어났을 때의 결과 자체는 ADR 0024가 이미 다루는 것과 같은 모양이다. 그래서 이
  ADR은 0024를 supersede가 아니라 **amend**한다 — supersede가 맞았을 경우는 아래 기각된
  "필드 완전 제거" 대안뿐이었을 것이다, 그건 실제로 ADR 0024의 분기를 도달 불가능하게
  만들었을 것이기 때문이다.
- **새 에러 코드**: 중복 제안용 409(D3), 대기중인 게 없는 상태에서 수락/거절/취소를 시도한
  경우의 typed 결과, 대기 대상이 아닌 사람이 수락/거절을 시도한 경우의 403. 순수 추가
  ([ADR 0011](0011-error-code-contract.ko.md)).
- **마이그레이션**: `FileEntity`에 `pendingTransferToUserId`(nullable, UserEntity FK) 추가
  — Scope Discipline에 따라 `migration:run` 전 라인 단위 검토.
- **`UpdateFileDto.userId` 제거.** 그 필드를 여전히 보내는 클라이언트는 조용한 no-op이
  아니라 전역 파이프의 `forbidNonWhitelisted`로 400 `VALIDATION_FAILED`를 받는다.
- **관리자가 수신자 동의 없이 파일을 강제 이전할 수 있는 능력을 잃는다.** 예전 필드는
  관리자가 아무 파일이든 아무 계정에게나 강제로 재배정할 수 있게 했는데, 이 결정이 그
  경로를 닫는다. 이 능력에 대한 모더레이션 용도가 명시된 적은 한 번도 없다(이 프로젝트엔
  모더레이션 기능 자체가 없음 — `docs/ROADMAP.md` Stage 5가 모더레이션 액션을 "없음"으로
  확정) — 그래서 제거되는 능력에 지금 의존하는 게 없다.
- **프론트엔드/admin UI는 이 ADR의 구현 범위 밖이다.** 제안/수락/거절/취소 액션과 상태
  배지는 `frontend/`/`admin/` 각자의 `CLAUDE.md`가 관할하는 별도 후속 작업으로 추적한다 —
  이 ADR의 구현은 백엔드만 다룬다.
- **새 엔드포인트 형태는 구현 시점에 결정** — 이 저장소의 기존 REST 관례를 따르며, 이
  ADR이 고정하는 건 상태 머신과 그 규칙이지 라우트 이름이 아니다.

## Alternatives rejected

- **필드 유지 + 근거만 문서화** — 기각: 이 ADR이 제기된 실제 문제(동의 없음, 강제 이전)를
  전혀 해결하지 못해 개발자가 밝힌 목적에 응답하지 않는다.
- **필드 완전 제거** — 기각: 이 API에 다른 경로가 없는, 이제 명확히 밝혀진 실제 필요(계정
  삭제 전 파일 이관)를 없앤다. 참고로 기록: 이게 바로 ADR 0024를 amend가 아니라 실제로
  supersede했을 유일한 대안이다 — ADR 0024의 `23503` 분기가 존재하는 유일한 경로 자체를
  없애기 때문이다.
- **제안·수락 시점 실시간 알림(이메일/푸시)** — 기각: 이 프로젝트 어디에도 알림 인프라가
  없다. 하나 만드는 건 이 결정의 범위를 훨씬 넘어서는 새 스코프다. 기존 파일 목록 표시와
  기존 "차단된 동작에 typed 거부"(`USER_HAS_FILES` 스타일) 패턴만으로 이미 충분한 정보를
  전달한다.
- **대기중인 제안을 새 제안으로 자동 덮어쓰기** — 기각: 이전 대상이 바뀌는 게 항상 제안자가
  직접 한 명시적 단계(D3의 `cancel`)이지, 다른 사람에게 제안한 부수 효과가 되지 않도록
  명시적 취소-후-재제안 방식을 선택.
- **여러 후보에게 동시에 제안, 먼저 수락하는 사람이 임자** — 기각: nullable 컬럼이 아니라
  별도 요청 테이블이 필요한데, 그럴 필요가 있다고 말한 적이 없다(YAGNI). D2의 단일 컬럼
  구조가 의도적으로 더 단순하다.
- **이전이 대기중이면 `DELETE ?deleteFiles=true`를 막아 수신자의 수락 기회를 보호** — 기각:
  이미 즉시 완료되는 typed 엔드포인트를 제3자의 결정을 기다리게 하거나 부분 완료 모드를
  갖게 만드는데, 이 ADR의 계정 삭제 유스케이스가 실제로 필요로 하는 보호가 아니다(D5).
