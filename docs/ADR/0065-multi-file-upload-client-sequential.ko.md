# ADR 0065: 여러 파일 업로드는 클라이언트가 파일 하나짜리 요청을 반복한다. 백엔드는 요청당 파일 하나를 유지한다

- Status: Accepted — `frontend/`(`UploadForm.tsx`)에 구현됨. 2026-10-06 로컬 compose 스택에서 검증(Playwright e2e)
- Date: 2026-10-06
- Relates to: [ADR 0003](0003-two-phase-upload-contract.ko.md) (파일마다 반복하는 2단계 계약), [ADR 0019](0019-upload-claim-idempotency.ko.md) (바뀌지 않고 그대로 동작하는 파일별 청구), [ADR 0027](0027-media-type-expansion-implementation.ko.md) (요청당 "`image`/`audio`/`video` 중 정확히 하나", 그대로 둔다), [ADR 0054](0054-per-route-rate-limit-tuning.ko.md) (한 번에 올릴 수 있는 수를 정하는 attach 분당 15회 한도), [ADR 0023](0023-board-domain-schema.ko.md) (게시글당 파일 하나, 이번 범위 밖)
- English: [0065-multi-file-upload-client-sequential.md](0065-multi-file-upload-client-sequential.md)

## Context

`POST /upload/attach`는 요청 하나에 파일 하나를 받는다. 세 필드가 각각 `maxCount: 1`로 등록돼 있고,
핸들러는 채워진 필드가 둘 이상이면 거부한다(`backend/upload/upload.controller.ts`). 업로드 폼도 그 모양
그대로였다. 제목 하나, 종류 라디오 하나, 파일 입력 하나라서, 파일이 네 개면 폼을 네 번 거쳐야 했다.

여러 파일 업로드를 따져 본 ADR은 지금까지 없었다. 파일 하나짜리 구조는 처음의 단일 `video` 필드에서
왔고, ADR 0025 D5와 ADR 0027이 필드를 셋으로 넓히면서 "정확히 하나"를 그대로 유지했다. 이 질문을 의도를
갖고 결정하는 것은 이 ADR이 처음이다.

지금 백엔드의 동작을 2026-10-05에 로컬 compose 스택에서 임시 계정으로 확인했다:

| 시도 | 결과 |
|---|---|
| 같은 필드에 파일 둘(`image` + `image`) | 400 `BAD_REQUEST`, "Unexpected field - image" |
| 한 요청에 `image` + `audio` + `video` | 400 `UPLOAD_MULTIPLE_FIELDS` |
| attach 요청 셋을 따로 | 각각 201 |
| 그 셋을 각각 `POST /file` | 각각 201, `mediaType`은 image / audio / video |
| 1분 안의 16번째 attach | 429 (거부된 요청도 횟수에 든다) |

즉 파일마다 요청을 따로 보내기만 하면 여러 파일은 지금도 올라간다.

## Decision

### D1 — 백엔드는 요청당 파일 하나를 유지하고, 클라이언트가 파일마다 요청을 하나씩 반복한다

폼에서 여러 파일을 한 번에 고르면, 파일마다 attach → promote를 차례로 실행한다. `backend/`는 바뀌지 않고
API 계약도 그대로다.

이유를 무게 순으로 적는다:

- 백엔드는 이미 요청 하나로 파일 하나를 받아 검사하고 이름을 붙여 등록한다. 여러 파일 업로드에 필요한
  것은 그 요청을 반복하는 것뿐이라, 서버에는 고칠 것이 없다.
- 파일 하나의 실패(스캔 거부, 제목 중복, 끊긴 연결)는 그 파일에서 끝난다. 나머지는 영향을 받지 않고, 그
  파일만 다시 보내면 된다.
- 업로드는 메모리에 버퍼링된다(`memoryStorage`, ADR 0029 D4). 요청당 파일이 하나면 한 요청이 쥐는 바이트는
  파일 하나, 최대 100MB를 넘지 않는다.

전송은 병렬이 아니라 순차다. 한 번에 요청 하나만 나간다.

### D2 — 파일 종류는 사용자가 고르지 않고 확장자로 정한다

종류 라디오를 없앴다. `UploadForm.tsx`가 파일마다 확장자를 `image`/`audio`/`video` 필드로 바꾸므로, 한 번의
선택에 종류가 섞여도 된다. 목록에 없는 확장자의 파일은 아무것도 보내기 전에 그 줄에 표시된다.

이로써 허용 확장자를 적어 둔 곳이 ADR 0040 D6이 든 백엔드의 세 곳에 더해 네 곳이 됐다. 확장자를 새로
받으려면 `UploadForm.tsx`의 `FIELD_BY_EXTENSION`도 함께 고쳐야 한다.

### D3 — 제목은 파일마다 하나, 기본값은 원본 파일명. 겹치면 그 줄에서 고친다

`FileEntity.title`이 unique라서 파일마다 제목이 따로 있어야 한다. 기본값은 확장자를 뗀 파일명을 그대로
쓴다. 겹치면 그 줄에 400 `FILE_TITLE_TAKEN`이 돌아오고, 사용자는 제목을 고쳐 업로드를 다시 누른다. 그때
파일은 이미 temp 저장소에 있으므로 promote 단계만 다시 시도하고 바이트는 다시 보내지 않는다.

### D4 — 한 번에 고를 수 있는 파일은 15개까지

attach는 분당 15회로 제한되고(ADR 0054) 파일 하나가 요청 하나다. 15개를 넘는 선택은 아무것도 보내기 전에
거절한다. 그래도 도중에 429가 돌아오면(같은 1분 안에 먼저 올린 것이 있을 때) 거기서 멈추고, 남은 줄은
다음에 누를 때를 위해 그대로 둔다.

### D5 — 게시글은 여전히 파일을 하나까지만 가리킨다

게시글 하나에 파일 여러 개를 붙이는 것은 이번 결정에 들어 있지 않다. `PostEntity.file`은 1:1이고 그 unique
제약은 `POST /post`의 멱등성 키이기도 해서(ADR 0023 D1/D4), 이를 푸는 것은 따로 결정해야 하는 스키마
변경이다. 둘은 서로 독립적이다. 그 결정을 다룰 때 이 ADR을 다시 볼 필요는 없다.

## Alternatives rejected

- **백엔드가 한 요청에 여러 파일을 받는다.** `maxCount`를 올리고 파일명 배열을 돌려주며 ADR 0025 D5와
  ADR 0027을 수정하는 방식이다. 기각: 한 요청의 최대 메모리가 파일 수만큼 커져서(파일 수 × 100MB) 총량
  상한이 필요해지고, "일부는 성공, 일부는 실패"인 응답을 새로 설계해야 하며, 모든 파일의 스캔 시간이 한
  요청 안에 쌓이고, 이 프로젝트의 규모에서는 요청 수를 줄여 얻는 것이 없다. 파일별 청구(ADR 0019)는 어느
  쪽이든 유지되므로, 멱등성은 찬성 이유도 반대 이유도 아니었다.
- **기본 제목에 구분값을 자동으로 붙여** 잘 겹치지 않게 한다. 기각: 제목은 사용자가 목록에서 보는 값이고,
  자동으로 붙은 꼬리는 읽기 나쁘게 만든다. 겹치면 그 줄에 표시되고 한 번 고치면 된다.

## Consequences

- 백엔드 변경, 스키마 변경, 새 에러 코드가 없다. `frontend/docs/API-CONTRACT.md`에는 클라이언트가 두 호출을
  어떻게 쓰는지에 대한 설명만 더해진다.
- 한 묶음을 올리는 데는 파일들의 전송·스캔 시간을 합한 만큼 걸리고, 한 번 눌러 올릴 수 있는 것은 15개까지다.
  지금 규모에서는 받아들인다.
- 올라간 파일은 서로 독립된 행이다. 한 번의 선택을 앨범이나 게시글로 묶는 것은 없다.
- 도중에 페이지를 떠나면 끝난 파일만 남고 나머지는 올라가지 않는다.
- attach 자체는 중복이 걸러지지 않는다. 다시 보내진 attach는 temp 파일을 하나 더 만들고, 이는
  `TEMP_SWEEP_TTL_HOURS` 뒤에 스윕이 지운다(ADR 0018, ADR 0019의 Consequences). promote 단계는 걸러진다.
  같은 `POST /file`이 다시 오면 200으로 재생된다.
- 같은 필드에 파일 둘을 보내면 여전히 타입이 없는 폴백 코드 `BAD_REQUEST`로 답한다. 이 폼은 그런 요청을
  보내지 않으므로 그대로 둔다.
- ADR 0019 추가 기록(2026-10-06)의 미청구 파일명 문제는 이 결정으로 달라지지 않는다.
- 파일마다 요청을 나누는 것은 다른 곳에서도 흔한 기본값이다. Uppy의 XHR 업로더는 `bundle`을 켜지 않으면
  파일마다 요청을 따로 보낸다([Uppy 문서](https://uppy.io/docs/xhr-upload/)).

2026-10-06에 로컬 compose 스택(`api`, `db`, `clamav`)과 Vite dev 서버로 검증했다:

- `e2e/upload.spec.ts` 3건: 영상 하나. 제목이 겹쳐 그 줄에서 실패한 뒤 제목을 고쳐 성공하고, attach 요청은
  정확히 한 번. 이미지·mp3·영상을 함께 골라 attach 요청 셋으로 세 줄이 올라감.
- `e2e/upload-select.spec.ts` 3건(API 스텁): 줄마다의 종류와 기본 제목, 허용되지 않는 확장자, 15개 상한과
  그 한국어 문구.
- `e2e/board.spec.ts`, `detail.spec.ts`, `posts.spec.ts`(10건)가 공용 헬퍼를 거쳐 새 폼으로 통과했고, 스텁
  기반 UI 테스트 16건도 통과했다. `navigation.spec.ts`의 `/files` 확인 두 곳은 이제 폼의 제목을 찾는다.
  Title 칸은 파일을 고른 뒤에만 생기기 때문이다.
- `frontend/`에서 `pnpm build`와 `pnpm lint`가 통과했다.

로컬 API는 rate limit이 켜져 있어서, 실제 백엔드를 쓰는 spec은 가입 분당 5회 한도를 넘지 않도록 1분 간격의
묶음으로 나눠 돌렸다. `pnpm test:e2e` 한 번으로 돌린 것은 아니다. 함께 돌리면 `navigation.spec.ts`의 직접
진입 테스트 두 건이 로그인 화면으로 떨어진다. 이번 변경 전 코드에서도 똑같고, 하나씩 돌리면 통과한다.
