# 문서 작성

CLAUDE.md의 Documentation Authoring Protocol을 실행 절차로 구체화한 것이다. 범위:
README.md, ARCHITECTURE.md, CHANGELOG.md, ROADMAP.md, CONTRIBUTING.md, `docs/ADR/` —
그리고 이들의 `.ko.md` 짝. 다섯 역할을 순서대로 실행한다; 단계를 합치지 않고,
앞선 역할이 끝나기 전에 글을 쓰기 시작하지 않는다.

## 1. 조사 (Investigate)

한 글자도 쓰기 전에 실제 코드, git history, 기존 문서를 읽는다. 모든 주장은 파일,
커밋, 또는 테스트 출력으로 추적 가능해야 한다 — 기억에 의존하지 않는다. 근거는
유효기간이 있다: 마지막으로 읽은 이후 무언가(커밋, 편집, 다른 세션)가 그 파일을
건드렸을 수 있다면, 그 근거로 결론 내리기 전에 다시 읽는다.

## 2. 계획 (Plan)

문서 집합, 각 문서의 범위, 그리고 전체 구조를 결정한다. 어떤 문서를 왜 바꾸는지
편집을 시작하기 전에 먼저 밝힌다.

## 3. 질문 (Question)

코드가 말해줄 수 없는 것을 추측하지 않는다. 구현 *의도*, 기술을 선택한 *이유*,
과거 결정의 *배경*은 소스가 아니라 개발자의 머릿속에 있다 — 글을 쓰기 전에
AskUserQuestion으로 먼저 물어본다. 선택형 질문 앞에는 반드시 옵션 × 기준의 간결한
표를 먼저 제시해서, 개발자가 산문이 아니라 표를 보고 결정하게 한다. 근거(rationale)는
확인된 뒤에만 적는다 — 추론해서 사실인 것처럼 적지 않는다.

## 4. 작성 (Write)

영문 문서를 먼저 쓰고, 같은 변경에서 `.ko.md` 짝을 쓴다(Documentation Convention —
자연스러운 한국어, 동일한 구조, 코드/경로/식별자는 그대로). 결과뿐 아니라 트레이드오프와
기각된 대안도 기록한다. 아키텍처적으로 유의미한 결정(스키마 변경, 새 모듈, 검토 후
기각된 대안)은 자체 ADR을 갖는다 — `adr-authoring` 스킬을 참고한다. 각 근거는 그
근거를 담고 있는 ADR이나 파일을 인용하고, 다시 풀어 쓰지 않는다.

## 5. 검증 (Verify)

- 상대 링크가 정상적으로 연결되는지
- EN/KO 구조가 대칭을 유지하는지 (같은 제목 구조, 같은 목록/표 레이아웃)
- 엔드포인트/동작에 대한 주장이 실제 라우트와 일치하는지 — grep으로 확인하고,
  눈대중으로 넘기지 않는다
- 실제로 커밋되지 않은 것을 완료된 것처럼 서술하지 않았는지

## 하지 않는다

- 3번의 질문에 답이 나오기 전에 글을 쓰지 않는다.
- 근거를 추론해서 사실처럼 제시하지 않는다 — 3번을 안 물어봤다면 돌아가서 물어본다.
- 아무리 작은 변경이라도 4번에서 `.ko.md` 짝을 건너뛰지 않는다.
