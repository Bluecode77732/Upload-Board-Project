# ADR 0021: 목록 조회 — 화이트리스트 정렬, ILIKE 제목 검색, 작성자 필터

- 상태: Accepted
- 결정일: 2026-07-30
- English: [0021-list-query-search-filter-sort.md](0021-list-query-search-filter-sort.md)

## 배경

ROADMAP Stage 3의 첫 항목은 "목록 검색 / 필터 / 정렬"이다. 게시판 목록의 데이터 계층 선행
작업이면서, 이후 post/comment 모듈이 새로 만들지 않고 물려받을 조회 계층이다. 이 ADR
이전의 `GET /file`은 `take`/`skip`만 받았다.

| 기능 | 이 ADR 이전의 동작 |
|---|---|
| 페이지네이션 | `take` 1–100(기본 20), `skip`(기본 0) — 2026-07-22에 추가된 `GetFilesDto` |
| 정렬 | **전혀 없음 — 쿼리에 `ORDER BY`가 아예 없다** |
| 제목 검색 | 없음 |
| 작성자 필터 | 없음 |

`ORDER BY`가 없다는 건 단순한 기능 공백이 아니다. PostgreSQL에서 정렬되지 않은 쿼리에
`OFFSET`/`LIMIT`을 얹으면 **행 순서가 미정의**다. 즉 `GET /file`을 페이지 단위로 넘기다가
어떤 행은 두 페이지에 중복되고 어떤 행은 아예 건너뛰어질 수 있었다 — 편의성 문제가 아니라
잠재적 정확성 버그다.

쿼리는 이미 `createQueryBuilder` 기반이고 `leftJoinAndSelect('file.creator')`를 하고 있으므로
확장 경로가 열려 있고 N+1 금지(Never Do Group 2)도 이미 충족돼 있다. 아래 설계 전체를
좌우한 제약은 하나다. 클라이언트가 보낸 정렬 키는 *컬럼명*이며, 이 코드베이스에서 요청
문자열이 SQL에 문자열로 합쳐질 수 있는 유일한 지점이다.

## 결정

**`GET /file`에 선택적 쿼리 파라미터 네 개 — `search`, `sortBy`, `order`, `creatorId` — 를
`GetFilesDto`에 선언해 추가하고, 정렬은 코드 내 화이트리스트만을 통해 해석한다. 응답 형태는
바꾸지 않는다.**

| 파라미터 | 허용 값 | 기본값 |
|---|---|---|
| `search` | 제목 부분일치, 100자 이하 | 없음 |
| `sortBy` | `createdAt` \| `title` \| `id` | `createdAt` |
| `order` | `DESC` \| `ASC` | `DESC` |
| `creatorId` | 양의 정수 | 없음 |

부수적 구현이 아니라 결정의 일부인 메커니즘:

- **정렬은 복합 문자열이 아니라 enum 파라미터 두 개(`sortBy` + `order`)다.** 검증은 `@IsIn`
  하나로 끝난다 — 정규식도 파싱 단계도 없으니 틀릴 파서 자체가 존재하지 않는다. Swagger에는
  열거형 드롭다운 두 개로 렌더링되어, 기존 DTO의 선언형 스타일(`GetFilesDto`,
  `DeleteUserQueryDto`)과도 결이 맞는다.
- **클라이언트 문자열은 컬럼명으로 쿼리에 도달하지 않는다.** `FILE_SORT_FIELDS`는 DTO에 둔
  리터럴 튜플이고, `FileService`는 그 튜플을 키로 하는 **완전한**
  `Record<FileSortField, string>`(`SORT_COLUMN`)을 갖는다. 튜플에 키를 추가하고 컬럼 매핑을
  빠뜨리면 **컴파일 에러**가 나므로, 화이트리스트가 쿼리와 조용히 어긋날 수 없다 — 리뷰
  습관이 아니라 구조가 보장한다.
- **화이트리스트는 스키마보다 의도적으로 좁다.** `filePath`도 정렬 가능한 컬럼이지만 제공하지
  *않는다*. 게시판에 쓸 데도 없이 저장소 내부 구조를 정렬 축으로 노출하는 일이다. 화이트리스트
  등재는 "동작하는 모든 컬럼"이 아니라 제품 결정이다.
- **기본 정렬은 `createdAt DESC`이고, `file.id`를 tiebreaker로 덧붙인다.** offset
  페이지네이션을 결정적으로 만드는 건 이 tiebreaker다. `createdAt`이(혹은 `title`이) 같은
  행들은 그것 없이는 두 번의 페이지 요청 사이에 순서가 뒤바뀔 수 있다. 이미 유일한
  `sortBy=id`일 때는 붙이지 않는다 — 두 번 붙여도 절만 중복될 뿐이다.
- **검색은 LIKE 메타문자를 이스케이프한 `ILIKE '%term%'`다.** 값은 파라미터로 바인딩되므로
  주입은 문제가 아니다. 문제는 이스케이프하지 않은 `%`나 `_`다. 사용자가 입력한 것보다 훨씬
  넓은 범위를 조용히 매칭시킨다(`_`는 임의의 한 글자와 매칭된다). 검색어의 `\`, `%`, `_`를
  이스케이프하고 쿼리에 `ESCAPE '\'`를 명시한다. 공백뿐인 검색어는 trim되어 미지정으로
  취급되므로, `?search=`가 빈 결과를 돌려주는 함정이 되지 않는다.
- **`creatorId`는 이미 있는 join을 통해 필터링한다** — 조건절 하나 추가, 추가 쿼리 없음,
  새 relation 로드 없음.
- **인덱스도, 스키마 변경도 없다.** 후보 인덱스 셋 다 이 테이블 규모에서는 측정 없는 추측이다
  (선제 최적화 회피). 각각을 정당화할 조건과 함께 "결과" 절에 기록해 둔다.
- **`FileService.getFiles`는 이제 위치 인자 `take, skip` 대신 DTO 객체를 받는다.** 위치 인자
  여섯 개는 호출부에서 두 개를 뒤바꿔 넣으라는 초대장이다. 컨트롤러는 이미 검증된 DTO를
  통째로 들고 있으니, 해석하지 않고 그대로 넘긴다.

## 검토 후 배제한 대안

- **복합 정렬 문자열(`?sort=createdAt:DESC`)** — 파라미터가 둘이 아니라 하나로 줄고, 나중에
  콤마로 다중 키 정렬까지 확장된다. 지금은 배제: enum 형태에는 필요 없는 수동 파싱(`@Matches`
  + 서비스에서 split)을 손으로 써야 하고, Swagger 문서화도 더 나쁘다. 다중 키 정렬이 실제로
  요구되면 다시 검토한다 — 그때도 화이트리스트 맵은 그대로 쓸 수 있다.
- **부호 접두사(`?sort=-createdAt`)** — 간결하고 주입 위험도 같이 없지만, 화이트리스트가
  필드 × 방향으로 두 배가 되고 `-` 규약이 타입이 아니라 산문 문서에만 남는다.
- **풀텍스트 검색(`to_tsvector` + GIN)** — 랭킹과 어간 처리를 얻는다. 배제: 작은 테이블의
  단일 컬럼 검색을 위해 스키마 변경(생성 `tsvector` 컬럼 + 인덱스)을 감수해야 하고, 한국어
  형태소 분석기 없이는 이 도메인의 제목에 필요한 부분어 매칭을 오히려 *잃는다*(`여행`으로
  검색해도 `해외여행`을 찾지 못한다) — 비용은 더 크고 정확도는 더 낮다.
- **`pg_trgm` 유사도** — 오타를 허용하고, `%term%`를 인덱스로 처리할 수 있게 만드는 유일한
  수단이다. 배제: 스캔이 문제라는 측정이 단 한 번도 나오지 않은 상태에서 확장 설치와
  마이그레이션을 요구한다.
- **접두사 전용 검색(`term%`)** — 평범한 b-tree로 처리 가능한 유일한 형태. 정확도 후퇴로
  배제: 제목 중간의 단어를 못 찾는 게시판 검색("holiday"로 "Summer Holiday Trip"을 놓친다)은
  기능의 목적 자체를 저버리며, 그 대가로 얻는 인덱스는 이 테이블에 아직 필요하지 않다.
- **`creatorEmail` 필터** — 숫자 id보다 사람에게 친절하지만, 목록 엔드포인트를 이메일 존재
  여부 확인 도구(열거 표면)로 바꿔 버린다. `creatorId`에는 그런 신호가 없고, 이메일을 아는
  클라이언트는 응답 본문에서 id도 이미 갖고 있다.
- **기간 필터(`from`/`to`)** — 추가는 쉽지만 그 뒤에 요구가 없다(YAGNI). "최신순으로 훑기"는
  정렬 화이트리스트가 이미 커버한다.
- **keyset(cursor) 페이지네이션** — offset이 흔들리는 문제의 구조적 해법이고, 깊은 `OFFSET`
  이후로도 확장된다. 여기서는 배제: 동결된 응답 계약([ADR 0010](0010-frontend-split-and-api-surface-freeze.ko.md))과
  클라이언트의 페이징 모델을 바꾸는 일이고, "페이지네이션은 유지하고 조회 능력을 얹는다"는
  이번 과제 범위를 벗어난다. 실제 결함이었던 비결정성은 `id` tiebreaker로 해소된다.

## 결과

- **`GET /file` 응답이 이제 정렬된 순서(최신순)로 돌아온다.** 이전에는 Postgres가 고른 순서
  그대로였다. 기존 호출자에게는 눈에 보이는 동작 변경이며, 동시에 배경에서 설명한 행
  중복/누락 위험의 수정이다. 응답 *형태*(`[files, totalCount]`)는 그대로이고 새 파라미터는
  모두 선택적이므로 동결된 API 표면(ADR 0010)은 유지된다 — 아무것도 보내지 않는 호출자는
  기존과 같게, 다만 결정적으로 동작한다.
- **새 에러 코드는 없다.** 모르는 `sortBy`/`order`, 100자를 넘는 `search`, 정수가 아닌
  `creatorId`는 모두 전역 파이프가 경계에서 400 `VALIDATION_FAILED`로
  거절한다([ADR 0011](0011-error-code-contract.ko.md)). 코드 추가는 비용이 없지만, 기존
  카탈로그가 이름 붙이지 못하는 결과가 여기엔 없다.
- **선언되지 않은 쿼리 파라미터는 무시가 아니라 거절이다.** `forbidNonWhitelisted` 덕분에
  `?orderBy=title` 같은 오타는 조용히 정렬 없는 목록이 되는 대신 400이 된다. 엄격 입력을
  택한 의도적 방침(Robustness Principle 미적용)이고, e2e 케이스로 고정해 두었다.
- **인덱스는 유보**하며, 각각을 도입할 계기를 함께 남긴다 — 셋 다 마이그레이션이 아니라
  평문 기술이다.
  - `("createdAt" DESC, "id" DESC)` — 매 요청 테이블을 정렬하는 대신 기본 정렬과 페이지
    경계를 인덱스에서 바로 읽게 한다. 행 수가 정렬 비용을 측정 가능하게 만들 때(대략 10⁴ 이상)
    정당화된다.
  - `pg_trgm` GIN on `lower(title)` — `ILIKE '%term%'`가 인덱스를 쓸 수 있게 되는 *전제
    조건*이다. 앞에 와일드카드가 오면 b-tree는 아무 도움이 안 된다. 확장 설치가 필요하므로
    2단계 마이그레이션이 된다.
  - `("creatorId")` — Postgres는 FK 컬럼에 인덱스를 자동 생성하지 않는다. 새 필터와 계정
    연쇄 삭제([ADR 0020](0020-account-deletion-cascade.ko.md)) 양쪽에 쓰인다.

  그때까지 `search`와 `creatorId`는 순차 스캔이고 정렬은 전체 정렬이다. 이 프로젝트 규모에서는
  그게 더 싼 선택이며, 이를 뒤집을 근거는 직관이 아니라 측정이어야 한다.
- **`search`는 100자로 제한**해, 호출자가 ILIKE 패턴을 임의로 길게 만들 수 없게 한다. 패턴
  매칭 비용은 입력 길이의 함수이고, 그보다 긴 정당한 제목은 없다.
- **이 조회 계층이 Stage 3 post 목록의 기준 패턴**이 된다: DTO에 선언된 파라미터, 완전한
  `Record` 정렬 화이트리스트, 이스케이프된 ILIKE, 정렬된 모든 페이지에 유일한 tiebreaker.
  post 모듈은 이 형태를 다시 서술하지 말고 확장해야 한다.
- **테스트**: `file.service.spec.ts`에 9개 케이스 추가(컬럼 매핑, tiebreaker 적용과
  `sortBy=id`일 때의 억제, 와일드카드 이스케이프, 공백뿐인 검색어, 필터, 조합)와 실제
  Postgres 기반 e2e 10개 추가 — 화이트리스트가 쿼리가 아니라 경계에서 강제된다는 것을
  증명하는 거절 케이스 두 개를 포함한다.
