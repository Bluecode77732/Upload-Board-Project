# ADR 0024: 계정 연쇄 삭제 — FK 위반 500 대신 타입 있는 거절

- 상태: Accepted
- 날짜: 2026-07-31
- English: [0024-account-cascade-fk-refusal.md](0024-account-cascade-fk-refusal.md)

## 배경

[ADR 0023](0023-board-domain-schema.ko.md) D1은 "게시글은 자기 작성자가 만든 파일만 참조한다"를
불변식으로 두고, 그 위에서 ADR 0020 계정 연쇄 삭제가 FK-safe하다고 논증했다. 계정의 게시글을 먼저
지우면, 곧 삭제될 파일을 가리키는 게시글은 남을 수 없다는 것이다.

post 모듈 구현 노트(2026-07-31)가 기록했듯 이 불변식은 생성 이후에는 실제로 성립하지 않는다. 이
ADR은 그에 대한 처방을 확정한다. ROADMAP이 comment 모듈 앞에 이 결정을 게이트로 세운 이유는, 후보
처방 하나가 comment 과제가 확장할 계정 연쇄의 삭제 순서를 바꾸기 때문이다.

**불변식이 깨지는 경로 — 4단계:**

1. A가 파일 F를 업로드한다 → `F.creator = A`.
2. A가 F를 첨부해 게시글 P를 작성한다. `FileService.assertAttachableBy`를 통과하고, 이 시점의
   불변식은 성립한다: `P.creator = F.creator = A`.
3. `PATCH /file/:id { userId: B }` → `F.creator = B`
   (`backend/file/file.service.ts`의 `updateFile` 안 `userId` 분기). 여기서 불변식이 깨진다:
   `P.creator = A`, `F.creator = B`.
4. `DELETE /user/B?deleteFiles=true` → `deletePostsOfCreator(B)`는 B의 게시글만 지우므로 A의 글인
   P는 살아남는다 → `deleteFilesOfCreator(B)`가 F를 지우려 한다 → `FK_post_entity_file`은
   `ON DELETE NO ACTION` → **`23503`**. 아무도 잡지 않아, ADR 0020이 없애려던 바로 그 불투명한
   500으로 새어 나간다.

3단계가 참조 중인 게시글을 확인하지 않는 이유는 서로 독립적인 세 가지이며, 셋 모두 처방을 제약한다.

| 사실 | 근거 | 영향 |
|---|---|---|
| 재배정 분기는 게시판 도메인보다 훨씬 먼저 존재했다 — ADR 0011(2026-07-23) 이전부터 있었고 `post_entity`는 2026-07-31에 들어왔다 | `backend/file/file.service.ts`에 대한 `git log -L` | 작성 시점에는 파일을 참조하는 것이 아무것도 없었다. 빠뜨린 한 줄이 아니라 낡은 전제다 |
| `FileService`는 `post_entity`를 조회할 수 없다 — `PostService`가 이미 `FileService`에 소유권을 묻고 있어 역방향 간선은 `forwardRef`가 필요한 모듈 순환이 된다 | [ADR 0023](0023-board-domain-schema.ko.md) D4 | `DELETE /file/:id`의 사전 조회를 막은 논거가 여기에도 그대로 적용된다 |
| `post.creatorId`와 `file.creatorId`를 묶는 제약이 없다. FK가 제약하는 것은 `post.fileId`뿐이다 | `backend/migrations/1785428640007-AddPostEntity.ts` | DB도 재배정을 거절하지 않는다 |
| `assertAttachableBy`는 `PostService.create`에서만 호출된다 | `backend/post/post.service.ts` | 불변식은 생성 시점에만 강제되고 이후 재검증되지 않는다 |

이 균열이 남기는 미처리 결과는 정확히 하나다. 재배정이 닿는 나머지는 이미 전부 타입이 붙어 있다.
재배정된 파일에 대한 `DELETE /file/:id`는 409 `FILE_IN_USE`로 답하고(D4), *참조하는 쪽* 게시글의
삭제는 언제나 FK상 적법하며, `PostService.resolveAttachment`에는 작성자 동일성 확인이 있어 파일의 새
소유자가 이전 소유자의 게시글을 replay로 건네받는 일이 없다. 오직 4단계의 `23503`만 500으로 빠져나간다.

## 결정

**그 `23503`을 `FileService.deleteFilesOfCreator`에서 타입 있는 409 `USER_FILES_IN_USE`로 번역한다.
불변식을 복원하지 않고, 재배정 엔드포인트를 좁히지 않으며, 연쇄 범위도 넓히지 않는다.**

계정 연쇄 삭제의 결과는 이렇게 정리된다.

| `DELETE /user/:id?deleteFiles=true` | 결과 |
|---|---|
| 다른 유저의 게시글이 이 계정의 파일을 참조하지 않음 | 기존과 동일 — 게시글 → 파일 → 유저 행, 그리고 커밋 뒤 unlink |
| 다른 유저의 게시글이 이 계정의 파일 중 하나를 참조함 | **409 `USER_FILES_IN_USE`**, 트랜잭션 전체 롤백, 아무것도 삭제되지 않음 |

번역을 `FileService`에 두는 이유는 두 가지다. 파일 행은 `UserService`의 트랜잭션 안에서도 여전히
`FileModule`의 책임이고([ADR 0020](0020-account-deletion-cascade.ko.md)), 형제 메서드인 `deleteFile`이
이미 똑같은 `23503` → 409 번역을 하고 있다. 이제 파일 행을 지우는 두 경로가 같은 클래스 안에서 참조를
같은 방식으로 처리한다.

사전 조회는 하지 않는다. D4가 이미 세운 두 이유 그대로다 — `File → Post` 모듈 순환이 생기고, 확인과
삭제 사이에 만들어진 게시글은 여전히 제약에 걸린다. DB를 판정자로 두는 쪽을 유지한다.
[ADR 0019](0019-upload-claim-idempotency.ko.md)가 `23505`에 쓴 기법의 세 번째 재사용이다.

거절 메시지는 문제의 게시글을 지목하지 않는다. 지목하려면 `post_entity` 조회가 필요한데 위 두 이유로
불가능하고, 애초에 실패 이후의 진단 조회 자체가 성립하지 않는다 — Postgres는 실패한 문장에서
트랜잭션을 abort시킨다. 지목 없이도 메시지는 행동 가능하다. 실패 시점에는 계정 *자신의* 게시글이 이미
삭제된 뒤이므로(삭제 순서 1단계), 남아서 참조 중인 게시글은 다른 유저의 것임이 증명된다.

`FILE_IN_USE`를 재사용하지 않고 새 코드를 만든 이유: 둘은 서로 다른 라우트에서 서로 다른 질문에
답한다("당신이 지목한 이 파일" 대 "이 계정이 가진 어떤 파일"). `DELETE /user/:id`에서 `FILE_IN_USE`를
받은 클라이언트는 어느 파일을 말하는지 알 수 없다. 코드 추가는 breaking change가 아니며
([ADR 0011](0011-error-code-contract.ko.md)), 이름은 같은 라우트의 다른 409인 `USER_HAS_FILES`와
의도적으로 대칭을 이룬다.

**`UserService.remove`의 삭제 순서는 그대로다.** 이것이 comment 모듈 게이트를 푸는 지점이다 — 이
결정을 다시 들추지 않고도 댓글 삭제를 게시글 앞에 끼워 넣을 수 있다.

## 검토 후 기각한 대안

- **복합 FK로 재배정 자체를 거절** — `file_entity`에 `UNIQUE (id, creatorId)`를 추가하고
  `post_entity`가 `(fileId, creatorId)`를 참조하게 만들어, Postgres가 3단계를 정면에서 거절하게 하는
  안이다. D1의 불변식을 "처리"가 아니라 *참*으로 만드는 유일한 후보이고, 판정을 DB가 하므로 모듈
  순환도 없다. 비용 대비 효용에서 기각했다. high-blast-radius 엔티티 두 개의 스키마 변경에다,
  복합 FK의 대상이 되기 위해서만 존재하는 중복 유니크 키를 `file_entity`에 추가하는 마이그레이션이
  필요하고, `post.creatorId`가 파일 쪽과 묶여 갱신 불가가 되며, 미처리 증상이 에러 코드 하나뿐인
  경로를 막자고 기존 기능(게시글에 걸린 파일의 admin 소유권 이관)을 영구히 제거한다. 폐기가 아니라
  기록으로 남긴다: 불변식이 *보장*으로 필요해지는 날 — 예컨대 `post.file`을 읽어 권한을 판정하는 기능이
  생긴다면 — 채택할 형태가 이것이며, 그때는 이 ADR을 확장하는 게 아니라 대체한다.
- **연쇄를 참조 게시글까지 확대** — 삭제되는 계정의 파일을 참조한다는 이유로 다른 유저의 게시글까지
  지운다. 두 가지 이유로 기각했다. 제3자 콘텐츠를 확인 없이 파괴한다 — ADR 0023 D5는 계정 삭제가 *그
  계정의 게시글에* 남들이 단 댓글을 가져가는 것까지는 수용했지만, 남이 작성한 게시글 전체를 가져가는
  것은 질적으로 더 큰 주장이고, 확인 플래그(`deleteFiles`)가 지목하는 대상은 파일이지 남의 글이
  아니다. 그리고 이것이 ROADMAP 게이트가 세워진 바로 그 후보다 — comment 모듈이 곧 확장할 삭제 순서를
  바꾸므로, 이를 택했다면 같은 순서를 두 번 고쳐야 했다.
- **`FileService.updateFile`에서 사전 조회로 불변식 복원** — "재배정 거절"의 직역이다. 현재 모듈
  그래프 안에서는 구현 자체가 불가능해 기각했다. `FileService`가 `post_entity`를 읽어야 하고(순환),
  확인과 갱신 사이에 생성된 게시글과는 여전히 경합한다.
- **500인 채로 두고 문서화만** — 아무것도 하지 않는 선택지이자 2026-07-31 이후의 현상 유지. 기각한다.
  예견 가능하고 클라이언트가 도달할 수 있는 실패가 불투명한 500으로 나타나는 것은 ADR 0020과 ADR
  0019가 없애려 한 결함 그 자체이고, CLAUDE.md는 새 쓰기 경로의 모든 예견 가능한 결과에 타입을 요구한다.

## 결과

- **새 에러 코드 하나**, `USER_FILES_IN_USE`(409). 순수 추가다
  ([ADR 0011](0011-error-code-contract.ko.md)).
- **계정 소유자의 잘못이 아닌 이유로 계정이 삭제 불가 상태가 될 수 있다** — 남의 게시글이 그 계정의
  파일을 참조하면 해당 게시글이 사라질 때까지 삭제가 거절된다. 막다른 길은 아니다. `canManage` 덕분에
  admin이 막고 있는 게시글을 지울 수 있고, 거절은 500이 아니라 행동 가능한 메시지를 가진 409다. 애초에
  선행 소유권 재배정이 있어야만 도달하는 좁은 경로이기도 하다.
- **post↔file 동일 작성자 규칙은 이제 불변식이 아니라 생성 시점 규칙이다.** ADR 0023 D1의 표현("FK
  위반이 구조적으로 도달 불가능하다")은 이 지점에서 대체된다 — 위반은 도달 가능하고, 이제 *처리*된다.
  이 성질에 보장으로서 기대려는 것은 무엇이든 위 복합 FK를 먼저 채택해야 한다.
- **`resolveAttachment`의 작성자 동일성 확인은 유지되고, 여전히 도달 가능하다.** 같은 균열의 다른 한쪽
  결과이며 이미 올바르다. 도달 불가능한 가드로 오인해 정리해서는 안 된다.
- **`PATCH /file/:id { userId }` 표면은 변하지 않는다** — 새 거절도, 새 검증도 없다. ADR 0007이 기술한
  동작 그대로다.
- **comment 모듈 게이트가 해제된다**: 이 결정은 `UserService.remove`의 삭제 순서를 건드리지 않으므로,
  ADR 0023 D5대로 댓글이 게시글 앞에 합류할 수 있다.
- **스키마 변경도 마이그레이션도 없다.** SQLSTATE 판별 헬퍼가 이미 있는 메서드에 `try`/`catch` 하나를
  더하는 것이 전부다.
